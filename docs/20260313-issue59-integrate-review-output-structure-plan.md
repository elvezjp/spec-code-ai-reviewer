# issue#59 分割レビュー統合結果の出力構造改善計画

## 概要

分割レビューの統合結果が設計書の章立て・項目名ではなくグループ単位で出力される問題を修正する。
一括レビューと同様に、設計書の章/項目名ベースで突合結果一覧が出力されるようにする。

## 背景

### 問題

同一の設計書・コード・システムプロンプトで一括レビューと分割レビューを実行した場合、
突合結果一覧の出力構造が異なる：

| レビュー種別 | 突合結果一覧の構造 |
|---|---|
| 一括レビュー | 設計書の章番号・項目名で整理される |
| 分割グループレビュー | 設計書の項目名で整理される（期待通り） |
| 分割統合結果 | グループID・グループ名で整理されてしまう |

### 原因分析

1. **標準レビュープリセットのformat**: `突合結果一覧（テーブル形式）` のみでカラム定義がない
2. **統合フェーズの入力構造**: `### グループ名 (groupId)` でグループ別に区切られており、LLMがグループ構造に引きずられる
3. **統合フェーズのnotes**: 「元々の設計書の構造を尊重してください」とあるが具体性が不足

## 修正方針

### 方針: フォールバックプロンプトの定数化 + プリセットのformat明示化 + 統合フェーズのプロンプト全面見直し

1. まずハードコードされたフォールバックプロンプトを定数に整理し、見通しを良くする（フェーズ0）
2. プリセットのformatで突合結果一覧のカラムを明示する（フェーズ1）
3. 統合フェーズのプロンプト（role/purpose/notes/ユーザーメッセージ）を全面見直しする（フェーズ2）

**効果**:
- フォールバック値が一覧でき、プリセットとの差異が把握しやすくなる

- 各エンドポイント関数がシンプルになる

### フェーズ1. 標準レビュープリセットのformat修正

**ファイル**: `versions/v0.9.1/frontend/src/core/data/presetCatalog.ts` L22-25

**現在**:
```
format: `マークダウン形式で、以下の順に出力してください：
1. サマリー（突合日時、ファイル名、総合判定）
2. 突合結果一覧（テーブル形式）
3. 詳細（問題点と推奨事項）`,
```

**修正後**:
```
format: `マークダウン形式で、以下の順に出力してください：
1. サマリー（突合日時、ファイル名、総合判定）
2. 突合結果一覧（テーブル形式: 項番, 設計書の章/項目名, 設計書の要件, コード箇所(行番号), 判定, 概要）
3. 詳細（問題点と推奨事項）`,
```

**効果**:
- 一括・グループ・統合のすべてで、設計書の章/項目名をカラムに含むテーブルが出力される
- グループレビュー時点で設計書項目名ベースの行が生成されるため、統合時のマージが容易になる

### フェーズ2. 統合フェーズ（Phase3）のプロンプト全面見直し

**ファイル**: `versions/v0.9.1/backend/app/routers/review.py`

統合フェーズのプロンプトを全面的に見直し、「グループ結果の統合」ではなく「下書きからの最終レポート作成」という位置づけに変更する。

#### 2-A. role の変更（L552）

**現在**:
```python
INTEGRATE_DEFAULT_ROLE = "レビュー結果を統合するエキスパート"
```

**修正後**:
```python
INTEGRATE_DEFAULT_ROLE = "設計書とプログラムコードの整合性を検証するレビュアー"
```

**理由**: 「統合エキスパート」だとグループ結果をまとめる作業者視点になりやすい。「レビュアー」として最終レポートを自分の言葉で再構成する意識を持たせる。

#### 2-B. purpose の変更（L556-567）

**現在**:
```python
# systemPromptありの場合
purpose = (
    "最終的な目的:\n```\n{purpose}\n```\n\n"
    "複数のグループに分けてレビューを行いました。"
    "各グループのレビュー結果を統合し、1つの最終的なレビューレポートを生成してください。"
)
# フォールバック
INTEGRATE_DEFAULT_PURPOSE = (
    "複数のグループレビュー結果を統合し、最終的なレビューレポートを"
    "Markdown形式で生成する"
)
```

**修正後**:
```python
# systemPromptありの場合
purpose = (
    "最終的な目的:\n```\n{purpose}\n```\n\n"
    "この目的に対するレビューを、作業効率のため複数の部分に分けて実施しました。"
    "各部分のレビュー結果（下書き）を元に、設計書の構造に沿った1つの最終レビューレポートを作成してください。"
)
# フォールバック
INTEGRATE_DEFAULT_PURPOSE = (
    "複数の部分に分けて実施したレビュー結果（下書き）を元に、"
    "設計書の構造に沿った最終レビューレポートをMarkdown形式で作成する"
)
```

**理由**: 「グループ結果を統合」→「下書きから最終レポート作成」に変えることで、グループ中心の思考を抑制し、設計書中心のレポート作成を促す。

#### 2-C. notes の変更（L577-581）

**現在**:
```python
INTEGRATE_DEFAULT_NOTES = [
    "- 各グループのレビュー結果を統合し、重複する指摘を排除してください",
    "- グループ分けは参考に止め、元々の設計書、コードの記載、構造を尊重してください。",
    "- 出力形式の指定に従い、全体を一括で評価した場合と同様になるよう出力してください。",
    "- マッチング処理やグループレビューで統合実行用に付与された付加情報は、レポートに含めないでください。",
]
```

**修正後**:
```python
INTEGRATE_DEFAULT_NOTES = [
    "- 【重要】突合結果一覧は、各部分のレビュー結果にある突合結果をマージし、"
    "設計書の章番号・項目名で整理してください。グループID・グループ名は出力に含めないでください。",
    "- 重複する指摘は排除し、矛盾がある場合は設計書の記載を優先して判断してください。",
    "- 出力形式の指定に従い、全体を一括で評価した場合と同じ形式で出力してください。",
    "- レビュー作業の分割に関する情報（グループ名、グループID、申し送り事項等）は最終レポートに含めないでください。",
]
```

**理由**: 「グループ名を使うな」を最重要項目として先頭に配置。「マッチング処理」等の内部用語も「レビュー作業の分割に関する情報」に言い換え。

#### 2-D. ユーザーメッセージのグループ見出し変更（L608-615）

**現在**:
```python
user_parts.append("## グループレビュー結果\n")
for gr in request.groupReviews:
    user_parts.extend([
        f"### {gr.groupName} ({gr.groupId})\n",
        gr.report if gr.report else f"**サマリー**: {gr.summary}\n",
        "",
    ])
```

**修正後**:
```python
user_parts.append("## 部分レビュー結果（下書き）\n")
for i, gr in enumerate(request.groupReviews, 1):
    user_parts.extend([
        f"### 部分{i}（参考: {gr.groupName}）\n",
        gr.report if gr.report else f"**サマリー**: {gr.summary}\n",
        "",
    ])
```

**理由**: 見出しを「部分N」に変えることで、グループ名の影響を抑制。グループ名は参考情報として残す。

#### 2-E. 構造マッチング結果JSONの簡略化（L598-606）

**現在**: 構造マッチング結果のJSONをそのまま渡している。

**修正後**: 統合時には不要なため削除する。

```python
# 構造マッチング結果は統合時には不要（レビュー作業の分割情報であり、最終レポートには不要）
# 削除: user_parts.extend([...構造マッチング結果...])
```

**理由**: グループ構造の詳細JSONが入力に含まれると、LLMがグループ構造を意識しやすくなる。設計書の構造は INDEX.md で十分把握できる。

#### フェーズ2の修正まとめ

| 箇所 | 変更内容 | 目的 |
|---|---|---|
| role | 「統合エキスパート」→「レビュアー」 | 最終レポート作成者視点に |
| purpose | 「グループ結果を統合」→「下書きから最終レポート作成」 | 設計書中心の思考に |
| notes | グループ名排除を最重要項目に、表現を具体化 | 出力構造を明確に制御 |
| ユーザーメッセージ見出し | `### グループ名 (groupId)` → `### 部分N（参考: グループ名）` | グループ名の影響を抑制 |
| 構造マッチングJSON | 削除 | グループ構造意識の排除 |

## テスト計画

- [ ] 一括レビュー: 突合結果一覧が設計書の章/項目名で出力されること

- [ ] 分割レビュー（統合）: 突合結果一覧がグループ名ではなく設計書の章/項目名で出力されること
- [ ] 分割レビューと一括レビューの突合結果一覧の構造が同等であること

## 備考

- 本修正はプロンプト変更のみであり、LLMの出力に依存するため、完全な保証はできない
- 効果が不十分な場合の次ステップ: 統合フェーズの入力構造変更（グループレビューの突合結果テーブルを事前マージして渡す）

# v0.8.0 セマンティック分割レビュー機能 実装計画書

**作成日**: 2026-02-04
**対象バージョン**: v0.8.0
**関連Issue**: [#37](https://github.com/elvezjp/spec-code-ai-reviewer/issues/37)

## 1. 概要

### 1.1 背景

現在のspec-code-ai-reviewerでは、設計書（Markdown変換後）とコード（行番号付与後）をそのままAIに渡してレビューを実行している。しかし、大規模なファイルの場合、AIの入力トークン上限を超えてレビューを実行できないケースがある。

### 1.2 解決策

md2map / code2map を使用して、ファイルを**意味のある単位**（セクション / クラス・関数）に分割し、逐次レビューを実行する機能を追加する。

| ツール | 対象 | 分割単位 |
|--------|------|----------|
| md2map | Markdown設計書 | 見出し（H1/H2/H3）単位 |
| code2map | ソースコード | クラス/メソッド/関数単位 |

### 1.3 実装方針

- v0.7.0ディレクトリを丸ごとコピーしてv0.8.0として作成
- 既存の一括レビュー機能はそのまま維持（後方互換性）
- 分割レビューはユーザーが明示的に選択する

---

## 2. 機能要件

### 2.1 分割モード

以下の4つのモードをサポートする。

| モード | 設計書 | コード | 説明 |
|--------|--------|--------|------|
| 一括（従来） | 一括 | 一括 | 従来通り全体を一度にレビュー |
| 設計書のみ分割 | 分割 | 一括 | 設計書が長大な場合 |
| コードのみ分割 | 一括 | 分割 | コードが長大な場合 |
| 両方分割 | 分割 | 分割 | 両方が長大な場合 |

### 2.2 分割実行の制御

- ユーザーが**明示的に**分割実行を選択する（自動判定は行わない）
- 分割設定は変換後、レビュー実行前に行う
- トークン数の目安を表示し、分割の必要性を判断できるようにする

### 2.3 レビュー結果

- 各パーツのレビュー結果を統合して1つのレポートとして出力
- 元ファイルの行番号へのマッピングを保持
- 分割レビューの場合、全体サマリーを最後に生成

## 4. バックエンド設計

### 4.1 一時ファイル管理（重要）

**バックエンドにファイルを残さない設計が必須。**

#### 4.1.1 一時ディレクトリ戦略

```python
# セッションごとに一意の一時ディレクトリを作成
import tempfile
import uuid
from pathlib import Path

class SessionFileManager:
    def __init__(self, session_id: str = None):
        self.session_id = session_id or str(uuid.uuid4())
        self.base_dir = Path(tempfile.gettempdir()) / "spec-code-reviewer" / self.session_id
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def cleanup(self):
        """セッション終了時に全ファイルを削除"""
        shutil.rmtree(self.base_dir, ignore_errors=True)

    def __enter__(self):
        return self

    def __exit__(self, *args):
        self.cleanup()
```

#### 4.1.2 クリーンアップのタイミング

| タイミング | 処理 |
|-----------|------|
| レビュー完了時 | 当該セッションの一時ファイルを削除 |
| エラー発生時 | finally句で確実に削除 |
| サーバー起動時 | 残存する古い一時ディレクトリを削除（TTL: 1時間） |
| 定期クリーンアップ | バックグラウンドタスクで古いファイルを削除 |

#### 4.1.3 詳細設計は後続タスクで検討

- 一時ファイルの暗号化要否
- ディスク使用量の上限設定
- 同時セッション数の制限
- クリーンアップのスケジューリング

### 4.2 新規APIエンドポイント

| Method | Path | 説明 |
|--------|------|------|
| POST | `/api/split/markdown` | Markdownをmd2mapで分割 |
| POST | `/api/split/code` | コードをcode2mapで分割 |
| POST | `/api/review/chunked` | 分割レビューを実行 |
| GET | `/api/review/chunked/{session_id}/status` | 分割レビューの進捗取得 |
| DELETE | `/api/session/{session_id}` | セッションのクリーンアップ |

### 4.3 データモデル

```python
from pydantic import BaseModel
from typing import List, Optional
from enum import Enum

class SplitMode(str, Enum):
    NONE = "none"           # 分割なし
    DOCUMENT = "document"   # 設計書のみ分割
    CODE = "code"           # コードのみ分割
    BOTH = "both"           # 両方分割

class DocumentPart(BaseModel):
    """分割された設計書パーツ"""
    section: str
    level: int
    path: str
    start_line: int
    end_line: int
    content: str
    estimated_tokens: int

class CodePart(BaseModel):
    """分割されたコードパーツ"""
    symbol: str
    type: str  # class, method, function
    start_line: int
    end_line: int
    content: str
    estimated_tokens: int

class SplitConfig(BaseModel):
    """分割設定"""
    document_split: bool = False
    document_max_depth: int = 2
    code_split: bool = False

class ChunkedReviewRequest(BaseModel):
    """分割レビューリクエスト"""
    session_id: str
    document_parts: Optional[List[DocumentPart]]
    code_parts: Optional[List[CodePart]]
    split_mode: SplitMode
    llm_config: dict
    review_options: dict

class ChunkedReviewProgress(BaseModel):
    """分割レビュー進捗"""
    session_id: str
    total_parts: int
    completed_parts: int
    current_document_part: Optional[str]
    current_code_part: Optional[str]
    status: str  # "running", "completed", "error"
    partial_results: List[str]
```

## 5. 分割レビューフロー

### 5.1 設計書のみ分割の場合

```
設計書パーツ1 + コード全体 → レビュー結果1
設計書パーツ2 + コード全体 → レビュー結果2
設計書パーツ3 + コード全体 → レビュー結果3
...
全レビュー結果 → 統合サマリー生成 → 最終レポート
```

### 5.2 コードのみ分割の場合

```
設計書全体 + コードパーツ1 → レビュー結果1
設計書全体 + コードパーツ2 → レビュー結果2
設計書全体 + コードパーツ3 → レビュー結果3
...
全レビュー結果 → 統合サマリー生成 → 最終レポート
```

### 5.3 両方分割の場合（重要）

設計書とコードの両方が分割されている場合、全組み合わせをレビューするとN×Mの計算量になる。これを効率化するため、以下の戦略を採用する。

#### 5.3.1 2段階レビュー戦略

```
【フェーズ1: 構造マッチング】
設計書INDEX.md + コードINDEX.md → AIに関連性を推定させる

AIプロンプト例:
"以下の設計書構造とコード構造を比較し、
 関連性の高いペアを特定してください。
 設計書の各セクションが、どのコード部分に対応するか推定してください。"

出力例:
{
  "pairs": [
    {"doc": "2. ユーザー管理機能", "code": ["UserService", "UserRepository"]},
    {"doc": "3. 認証機能", "code": ["AuthService", "TokenManager"]},
    ...
  ],
  "orphans": {
    "doc": ["1. 概要", "付録A"],  // コードに対応しない設計書セクション
    "code": ["Utils"]              // 設計書に対応しないコード
  }
}
```

```
【フェーズ2: ペアレビュー】
関連性の高いペアのみをレビュー

設計書パーツ「2. ユーザー管理機能」 + コード「UserService」 + コード「UserRepository」
    → レビュー結果1

設計書パーツ「3. 認証機能」 + コード「AuthService」 + コード「TokenManager」
    → レビュー結果2

...

孤立パーツ（設計書のみ/コードのみ）
    → 個別に軽量レビュー（対応がないことを指摘）
```

```
【フェーズ3: 統合】
全レビュー結果 + 構造マッチング結果
    → 統合サマリー生成
    → 最終レポート
```

              │ - サマリー生成            │
              └─────────────┬────────────┘
                            │
                            ▼
              ┌──────────────────────────┐
              │ 最終レビューレポート       │
              └──────────────────────────┘
```

### 5.4 AIへの入力形式

#### 5.4.1 フェーズ1: 構造マッチング用プロンプト

```markdown
# 構造マッチング依頼

以下の設計書構造とコード構造を比較し、関連性の高いペアを特定してください。

## 設計書構造 (INDEX.md)

{設計書のINDEX.md内容}

## コード構造 (INDEX.md)

{コードのINDEX.md内容}

## 出力形式

以下のJSON形式で出力してください:

```json
{
  "pairs": [
    {
      "document_section": "セクション名",
      "document_path": "parts/xxx.md",
      "code_symbols": ["ClassName", "ClassName#methodName"],
      "code_paths": ["parts/xxx.py", "parts/yyy.py"],
      "confidence": "high|medium|low",
      "reason": "マッチング理由"
    }
  ],
  "orphan_documents": ["対応コードがないセクション"],
  "orphan_code": ["対応設計書がないシンボル"]
}
```
```

#### 5.4.2 フェーズ2: ペアレビュー用プロンプト

```markdown
# レビュー依頼

以下の設計書セクションとコードの整合性をレビューしてください。

## レビュー対象

- 設計書セクション: {セクション名}
- 対応コード: {シンボル名リスト}

## 設計書内容

{設計書パーツ内容（ヘッダコメント含む）}

## コード内容

{コードパーツ内容（ヘッダコメント含む）}

## レビュー観点

1. 設計書の記述とコード実装の整合性
2. 設計書に記載があるがコードに実装されていない機能
3. コードに実装があるが設計書に記載がない機能
4. 命名の一貫性
5. その他の懸念事項

## 出力形式

以下の形式でレビュー結果を出力してください:

### 整合性サマリー
[全体的な整合性の評価]

### 詳細指摘事項
| # | 種別 | 設計書行 | コード行 | 内容 |
|---|------|----------|----------|------|
| 1 | 不整合 | L25-30 | L45-50 | ... |
```

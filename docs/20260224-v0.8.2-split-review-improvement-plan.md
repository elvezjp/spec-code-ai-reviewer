# v0.8.2: 分割レビュー品質改善（3件）

作成日: 2026-02-24

## 背景

分割レビュー機能を実際の設計書・プログラムで利用した際に、以下の3つの問題が確認された。

1. 設計書を含まないグループが作成されてしまう
2. 全グループで重要なシートを参照したい
3. メソッドが未実装と指摘されてしまう

いずれも分割レビューのグルーピング・グループレビューの品質に関わる問題であり、プロンプト改善・UI追加・API拡張で対応する。

## ゴール

- 構造マッチングで、設計書セクションとコードシンボルの**両方が必ず1件以上含まれるグループ**のみ生成される
- 分割プレビュー時に**重要パートを選択**し、全グループのレビューで共通参照される
- グループレビュー時に**設計書・コード全体の構造情報（INDEX.md / MAP.json）がAIに渡される**ことで、他グループに実装されている関数を「未実装」と誤指摘しなくなる

## 非ゴール

- 構造マッチングのアルゴリズム自体の変更（LLMベースのまま）
- 対応言語の追加（Python / Java のまま）
- 分割プレビューUIの大幅なデザイン変更

## 改善3: メソッドが未実装と指摘されてしまう

### 問題の詳細

グループレビュー（フェーズ2）では、そのグループに割り当てられた設計書セクションとコードシンボルのみがAIに渡される。そのため、他のグループに含まれるメソッドや関数が存在しないものと判断され、「未実装」と誤指摘されてしまう。

### 実装方針

グループレビューAPIのリクエストに全体の構造情報（INDEX.md / MAP.json）を追加し、プロンプトでも「全体の一部をレビューしている」ことを強調する。

## 追加改善1: AIモード分割で最後のグループが巨大になる

### 問題の詳細

AIモード（`splitMode: "ai"`）でMarkdownを分割する際、md2mapの `MarkdownParser` に渡す `max_subsections` がデフォルト値の5のままとなっている。
セクションの文字数が大きい場合（例: 60,000文字）、本来は `ceil(60000/500) = 120` 分割が必要だが、`min(5, 120) = 5` に制限される。
その結果、LLMは「最大5つに分割」という指示を受け、冒頭の小さな意味のまとまりを4グループに分割した後、残りの大部分（例: 59,200トークン）を最後の1グループにまとめてしまう。

```
例:
  グループ1: L41-L49   (~59トークン)
  グループ2: L50-L60   (~4,033トークン)
  グループ3: L61-L68   (~6,922トークン)
  グループ4: L69-L78   (~9,464トークン)
  グループ5: L79-L161  (~59,200トークン)  ← 最後のグループに偏る
```

### 原因

1. `split.py` で `MarkdownParser` を生成する際に `max_subsections` を指定していないため、デフォルトの5が使用される
2. md2mapの `_refine_sections()` で `target_parts = min(max_subsections, ...)` により分割数が5に制限される
3. LLMプロンプトに均等性の制約がないため、LLMが不均等な分割を行う

### 実装方針

`max_subsections` を環境変数 `MD2MAP_MAX_SUBSECTIONS` で設定可能にする。デフォルト値はmd2mapライブラリと同じ5を維持する。

### Step 4-a. 環境変数の追加

対象: `.env.example`

追加:
```

```

## 追加改善2: 実行画面の表示不具合と対応なしグループのスキップ

### 問題の詳細

構造マッチング結果の実行画面で以下の問題が発生している。

#### 問題A: 設計書セクション・コードシンボルの表示がカンマのみ

実行画面のグループ一覧テーブルおよびグループステップカードで、設計書セクション名・コードシンボル名がカンマ区切りの空文字（`, , , , ,`）として表示される。

**原因:** Step 1-eで導入したMAP.json復元処理のフィールド名不一致。

| 対象 | MAP.jsonの実際のフィールド名 | 復元コードが参照しているフィールド名 |
|------|--------------------------|-------------------------------|
| 設計書セクション名 | `section` (md2map生成) | `title` |
| コードシンボル名 | `name` (フロントエンド構築) | `symbol` |

- md2mapが生成するMAP.jsonでは、セクション名が `section` フィールドに格納される（`title` ではない）
- フロントエンドがコードMAP.jsonを構築する際、シンボル名を `name` フィールドに設定する（`symbol` ではない）
- 復元コードがこれらの実際のフィールド名と異なるフィールド名で取得するため、空文字が返される

#### 問題B: 「（分割なし）」表示が不正確

doc_sectionsまたはcode_symbolsが空のグループで「（分割なし）」と表示されるが、正しい表現は「対応なし」。分割されていないのではなく、対応する設計書/コードがないケースであるため。

#### 問題C: 対応なしグループで不要なレビュー実行

doc_sectionsまたはcode_symbolsが空のグループ（設計書またはコードの対応がないグループ）でもグループレビューAPIが呼び出される。対応がない場合はレビュー不要であり、APIコール・トークン消費を避けるべき。

### 実装方針

- バックエンドのMAP.json復元コードを削除し、IDのみで返却する（問題A根本解決）
- フロントエンドで `documentParts` / `codeParts` からグループ情報を補完する（問題A）
- バックエンドの `allGroups` テーブルをシンボル名からID表示に変更する（問題A関連）
- フロントエンドの表示テキストを修正（問題B）
- フロントエンドのグループレビューループで対応なしグループを自動スキップ（問題C）

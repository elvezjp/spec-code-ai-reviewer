# 結合テスト・シナリオテストのガイドライン素案

単体テストだけでは検出できない問題（環境差異、セットアップ手順の不備、クロスプラットフォーム問題など）を防ぐため、結合テスト・シナリオテストの方法を定めます。最終承認者は田中社長です。

## 背景

単体テストが全てパスしていても、以下のような問題は検出できない:

- Windows環境でファイル名の禁止文字によりgit cloneが失敗する
- READMEの手順通りにセットアップしても依存関係が不足している
- 生成物のパス参照が実在しないファイルを指している

これらは「別の環境で実際に動かす」ことで初めて発覚する。本ガイドラインでは、3つの手法を組み合わせてこれらの問題を防ぐ。

## 手法一覧

| 手法 | 目的 | 実行タイミング | 実行者 |
|------|------|--------------|--------|
| CI（GitHub Actions） | クリーン環境での自動検証 | PR作成時・マージ時 | 自動 |
| AIレビュー | リリースして問題ないかの静的チェック | リリース前 | AI |
| シナリオテスト | ユーザー視点での動的な動作検証 | リリース前 | AI＋人間 |

## 1. CI（GitHub Actions）

### 目的

PR ごとにクリーンな環境で clone → セットアップ → テスト実行を自動で行い、環境依存の問題を検出する。

### 必須構成

公開リポジトリでは、以下を最低限のCI構成とする。

#### マルチOS・マルチバージョンでの単体テスト実行

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        # Python の場合
        python-version: ["3.9", "3.12"]
        # Node.js の場合
        # node-version: ["18", "22"]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - name: Install dependencies
        run: pip install -e ".[dev]"
      - name: Run tests
        run: pytest
```

#### CI で検証されること

| 検証項目 | 説明 |
|---------|------|
| git clone の成功 | ファイル名にOS禁止文字が含まれていないこと |
| 依存関係のインストール | 必要なパッケージが全て解決できること |
| 全テストの通過 | 単体テスト・E2Eテストがクリーン環境で通ること |
| クロスプラットフォーム | Windows / macOS / Linux で動作すること |

#### 追加推奨: ファイル名ガードレール

リポジトリ内のファイル名にOS禁止文字が混入することを防ぐステップ。

```yaml
- name: Check filenames for OS-incompatible characters
  run: |
    python -c "
    import pathlib, sys
    invalid = set('<>:\"|?*')
    bad = [str(p) for p in pathlib.Path('.').rglob('*') if invalid & set(p.name)]
    if bad:
        print('OS-incompatible filenames found:')
        for b in bad: print(f'  {b}')
        sys.exit(1)
    "
```

### 運用ルール

- 全テストがパスしない限り、main ブランチへのマージは不可
- CI の設定ファイル（`.github/workflows/`）を変更する場合はレビュー必須

## 2. AIレビュー

### 目的

リリース前に、AIエディタ（Claude Code、Cursor等）を使ってコードを静的にチェックし、**リリースして問題ないか**を確認する。開発中の補助ではなく、リリース可否を判断するための**試験工程**として実施する。

### シナリオテストとの違い

| | AIレビュー | シナリオテスト |
|---|---|---|
| 観点 | コードに問題がないか（静的） | 動かして問題がないか（動的） |
| 対象 | ソースコード・設定ファイル | 実行結果・ユーザー体験 |
| 手法 | コードを読んで判定 | 実際にコマンド・操作を実行して判定 |

### レビュー観点

#### 共通観点（全リポジトリ共通）

以下の観点を共通のチェックリストとして管理し、AIに渡す。

**クロスプラットフォーム**

- ファイル名にOS禁止文字が含まれないか（`< > : " / \ | ? *`）
- パス結合に `os.path.join` / `pathlib` を使っているか（`"/"` のハードコードがないか）
- 大文字小文字だけが異なるファイル名が存在しないか
- 改行コードが混在していないか

**セキュリティ**

- シークレットやクレデンシャルがコードに含まれていないか
- ユーザー入力がサニタイズされているか

**可搬性・セットアップ**

- READMEの手順通りにセットアップが完結するか
- 暗黙の前提条件（特定ツールのインストール等）がないか
- 言語・ランタイムのバージョン指定が適切か

#### プロジェクト固有の観点

各リポジトリの CLAUDE.md 等に、プロジェクト固有のレビュー観点を記載する。

```markdown
# プロジェクト固有のレビュー観点（例: code2map）
- 生成ファイル名がファイルシステム安全か
- MAP.json の part_file が実在パスを指しているか
```

### 試験項目一覧と結果報告

シナリオテストと同様に、チェックリストに基づいて実行し、結果報告を残す。

```markdown
# AIレビュー結果報告

実行日: 2026-02-26
実行者: Claude Code
対象: プロジェクト名 vX.Y.Z

| # | レビュー観点 | 結果 | 備考 |
|---|------------|------|------|
| 1 | ファイル名にOS禁止文字がない | OK | |
| 2 | パス結合にハードコードがない | OK | |
| 3 | シークレットがコードに含まれない | OK | |
| 4 | README手順でセットアップ完結する | NG | Node.js 18以上が必要だが未記載 |
```

### 実行方法

リリース前に、AIエディタで以下のように依頼する。

```
リリース前のAIレビューを実施してください。
レビュー観点チェックリストに基づき、全項目を確認し、結果報告を作成してください。
```

### 注意点

- AIレビューの結果は人間が確認し、最終的なリリース可否は人間が判断する
- NG項目がある場合は、修正後に再度レビューを実施する

## 3. シナリオテスト

### 目的

ユーザーの視点で、セットアップから基本的な操作までの一連の流れを検証する。AIが実行可能な項目はAIが担当し、人間の操作が必要な項目は人間が担当する。

### ファイル構成

各リポジトリの `docs/` 配下に以下のファイルを配置する。

```
docs/
├── test-scenarios.md         # シナリオ定義（手順の流れ）
├── test-checklist.md          # 試験項目一覧（チェックリスト）
└── test-results-YYYYMMDD.md   # 結果報告（実行ごとに生成）
```

### シナリオ定義（test-scenarios.md）

ユーザーが実際に行う操作の流れを記述する。

```markdown
## シナリオ1: 初回セットアップ
1. リポジトリを clone する
2. README に記載された手順でインストールする
3. ヘルプコマンドが正常に表示されることを確認する

## シナリオ2: 基本的な使用
1. サンプル入力ファイルに対してコマンドを実行する
2. 出力ファイルが生成されることを確認する
3. 出力内容の整合性を確認する

## シナリオ3: エラーケース
1. 不正な入力を与えて、適切なエラーメッセージが出ることを確認する
```

### 試験項目一覧（test-checklist.md）

シナリオを具体的な試験項目に分解する。各項目に**実行者**（AI / MANUAL）を明記する。

```markdown
## シナリオ1: 初回セットアップ

| # | 試験項目 | 実行 | 判定基準 |
|---|---------|:----:|---------|
| 1-1 | clone が成功する | AI | 終了コード 0 |
| 1-2 | 依存関係のインストールが成功する | AI | エラーなし |
| 1-3 | ヘルプコマンドが表示される | AI | 使用方法が出力される |

## シナリオ2: 基本的な使用

| # | 試験項目 | 実行 | 判定基準 |
|---|---------|:----:|---------|
| 2-1 | コマンドが正常終了する | AI | 終了コード 0 |
| 2-2 | 出力ファイルが生成される | AI | 所定のファイルが存在 |
| 2-3 | 出力ファイルの内容が妥当 | AI | JSONが有効、参照パスが実在 |
| 2-4 | 別OSで出力をclone可能 | MANUAL | Windowsでgit clone成功 |
```

#### 実行者の定義

| 実行者 | 意味 |
|-------|------|
| **AI** | AIエディタが自動で実行・判定できる |
| **MANUAL** | 人間の操作が必要（ファイル選択ダイアログ、別OS確認、外部サービス連携等） |

### 結果報告（test-results-YYYYMMDD.md）

テスト実行後、AIまたは人間が結果を記入する。

```markdown
# テスト結果報告

実行日: 2026-02-26
実行者: Claude Code / 担当者名
対象: プロジェクト名 vX.Y.Z

## シナリオ1: 初回セットアップ

| # | 試験項目 | 結果 | 備考 |
|---|---------|------|------|
| 1-1 | clone が成功する | OK | |
| 1-2 | 依存関係のインストールが成功する | OK | |
| 1-3 | ヘルプコマンドが表示される | OK | |
```

#### 結果ステータス

| ステータス | 意味 |
|-----------|------|
| **OK** | 期待通り動作した |
| **NG** | 期待と異なる動作。備考に詳細を記載する |
| **SKIP** | 環境の制約等で実行できなかった |
| **MANUAL** | 人間の操作が必要な項目で、未実施 |

### 人間の操作が必要な項目の例

シナリオ作成時に、AIでは実行できない操作を事前に把握しておく。

#### CLIツールの場合

| 操作 | AI | 人間 | 理由 |
|------|:---:|:---:|------|
| コマンド実行・出力確認 | 可 | | |
| ファイルの中身の検証 | 可 | | |
| OS権限の変更が必要な操作 | | 要 | セキュリティ上の制約 |
| 別OSでの実行確認 | | 要 | 実行環境が限定される |

#### Webアプリの場合

| 操作 | AI | 人間 | 理由 |
|------|:---:|:---:|------|
| ページ遷移・クリック | 可 | | AIブラウザ拡張で対応 |
| テキスト入力・フォーム送信 | 可 | | AIブラウザ拡張で対応 |
| 画面の表示確認 | 可 | | スクリーンショットで判定 |
| ファイル選択ダイアログ | | 要 | OSネイティブUIは操作不可 |
| CAPTCHA | | 要 | 自動操作を防ぐ仕組み |
| 二要素認証（SMS/アプリ） | | 要 | 外部デバイスが必要 |
| 印刷プレビュー | | 要 | ブラウザネイティブUI |
| 外部サービス連携の確認 | | 要 | メール受信、Slack通知等 |

### シナリオテストの実行方法

AIエディタで以下のように依頼する。

```
docs/test-checklist.md の試験項目を順番に実行し、
結果を docs/test-results-YYYYMMDD.md に記録してください。
MANUAL の項目はスキップし、結果に MANUAL と記載してください。
```

実行後、MANUAL 項目を人間が確認し、結果を追記する。

## 各手法の使い分け

```
PR 時（自動）              リリース前（試験）
───────────────          ──────────────────────────
CI                       AIレビュー（静的チェック）
・マルチOS検証              ・クロスプラットフォーム観点
・単体テスト全通過           ・セキュリティ観点
・ファイル名ガードレール      ・可搬性・セットアップ観点
                          ・結果報告を残す

                         シナリオテスト（動的チェック）
                          ・セットアップ手順の実行（AI）
                          ・基本操作の動作確認（AI）
                          ・別OS確認等（人間）
                          ・結果報告を残す
```

| 観点 | CI | AIレビュー | シナリオテスト |
|------|:---:|:---:|:---:|
| 実行タイミング | PR時（自動） | リリース前 | リリース前 |
| 性質 | 自動テスト | 静的チェック | 動的チェック |
| 自動化・再現性 | 高 | 中 | 中 |
| クロスプラットフォーム | 検証可 | 指摘のみ | 一部（MANUAL） |
| 結果報告 | 自動（Pass/Fail） | 手動で記録 | 手動で記録 |
| 導入コスト | 低 | 低 | 中 |

## 公開リポジトリでの最低要件

公開リポジトリでは、以下を最低限のテスト体制とする。

1. **CI**: マルチOS での clone → インストール → テスト実行
2. **試験定義**: AIレビュー観点とシナリオテスト項目を `docs/` に記載
3. **リリース時**: AIレビューとシナリオテストを実施し、結果報告を残す

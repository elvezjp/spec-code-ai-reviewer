# v0.8.3 / v0.9.0: LLMモダナイゼーション計画

作成日: 2026-07-15

> **ステータス**: Part 1（v0.8.3）実装完了（2026-07-15）。Part 2（v0.9.0）は未着手。
> 本計画書はコードベース全体調査（バックエンド・フロントエンド・インフラの3方向）に基づく次期バージョンの提案。

## 背景/問題

v0.8.2 のリリース（2026-02-21）から約5ヶ月が経過し、LLMまわりを中心に以下の点が古くなっている。

### 1. LLMの使い方が2025年前半の水準のまま

- **モデルデフォルトが旧世代**: 設定ファイルジェネレーターのデフォルトが `claude-sonnet-4-5-20250929` / `gpt-4o` 世代（`frontend/src/features/config-file-generator/schema/configSchema.ts`）。現行世代（Claude Sonnet 5 / Opus 4.8 等）は**コンテキスト1Mトークン・出力128K**で、レビュー可能な規模の前提が変わっている。
- **プロンプトキャッシュ未使用**: 一括レビューは**同一入力を必ず2回**実行する設計（`useReviewExecution.ts` の `REVIEW_EXECUTION_COUNT = 2`）だが、キャッシュを使っていないため2回目も全額課金される。キャッシュを使えば2回目の入力コストが約1/10になる。
- **Structured Outputs 未使用**: 分割レビューのフェーズ1（構造マッチング）は「プロンプトでJSONを出すよう誘導し、正規表現で ```json ブロックを抽出」する方式（`backend/app/routers/review.py` の `_extract_json`）で、パース失敗のリスクがある。
- **ストリーミング未使用**: 全LLM呼び出しが同期一括。フロントに「5分以上かかるとタイムアウトの可能性」と注記せざるを得ない。
- **トークン推定が3方式4箇所に散在**: `review.py` / `split.py`（日本語1.5トークン/字）、`markdown_organizer.py`（len/4）、フロント `useTokenEstimation.ts`（正規表現方式）。しきい値 `WARNING_THRESHOLD = 100000` もハードコードで、現行モデルの実上限と無関係。

### 2. 信頼性・セキュリティの穴

- ルーターは `async def` だがLLM呼び出しは同期SDKを直接呼びイベントループをブロック（`organize.py` のみ `asyncio.to_thread` 使用で一貫性がない）。
- リトライは organize のみ。一括レビュー・分割レビュー3フェーズにリトライなし。
- `CORS_ORIGINS` 未設定時に `allow_origins=["*"]` + `allow_credentials=True`（`backend/app/main.py`）。
- エラーレスポンスに内部例外文字列をそのまま露出（`f"...: {str(e)}"` 多数）。
- アップロードファイル名を未検証のまま tempfile 内パスに使用（`split.py`、excel2mdツール）。

### 3. プロバイダー実装の重複

`bedrock_service.py` / `anthropic_service.py` / `openai_service.py` の `execute_review` / `send_message` / `organize_markdown` / `test_connection` はAPI呼び出し部以外ほぼ同一コード。リトライ・タイムアウト・キャッシュ等の横断機能を入れる際の障害になる。

## ゴール

- **v0.8.3（小規模・効果即出）**: モデルデフォルトの現行化、プロンプトキャッシュ導入、セキュリティ修正
- **v0.9.0（中核）**: Structured Outputs によるフェーズ1堅牢化、ストリーミング対応、トークン推定の一元化としきい値再調整、LLM呼び出しの非同期化・共通化

## 非ゴール

- フロントエンドUI刷新（Markdownレンダリング・アクセシビリティ改善）→ 別計画（v0.9.x）で対応
- CI/CD導入・マルチバージョン運用の自動化 → 別計画（v1.0.0 に向けて）で対応
- code2map の対応言語拡張 → 別計画で対応
- 旧バージョン（v0.8.2以前）へのバックポート

## 作業方針

従来どおり `versions/v0.8.2` を `versions/v0.8.3` にコピーして v0.8.3 の変更を行い、リリース後に `versions/v0.8.3` → `versions/v0.9.0` をコピーして v0.9.0 の変更を行う。

- v0.8.3 のポート番号: `8000 + (8 × 10) + 3 = 8083`
- v0.9.0 のポート番号: `8000 + (9 × 10) + 0 = 8090`

## Step 2: プロンプトキャッシュ導入

一括レビューの「同一入力2回実行」と、分割レビューの「共通設計書 × 複数グループ」でキャッシュが効く。

### 2-a. Anthropic: `cache_control` の付与

対象: `versions/v0.8.3/backend/app/services/anthropic_service.py`

- `messages.create` の `system` をブロック形式にし、最後のブロックに `cache_control: {"type": "ephemeral"}` を付与
- ユーザーメッセージ（設計書＋コード本文）は content ブロック配列にし、末尾ブロックに `cache_control` を付与
- レスポンスの `usage.cache_read_input_tokens` / `cache_creation_input_tokens` をログ出力（効果測定用）

**注意**: キャッシュはプレフィックス一致。1回目と2回目のリクエストでプロンプトがバイト単位で同一であることを確認する（現状は同一のはずだが、タイムスタンプ等を混ぜないこと）。最小キャッシュ対象トークン数（モデルにより1024〜4096）未満の小規模入力ではキャッシュされないが、エラーにはならない。

### 2-b. Bedrock: Converse API の cachePoint 対応

対象: `versions/v0.8.3/backend/app/services/bedrock_service.py`

Converse API の `cachePoint` ブロックを system / messages に挿入する。**モデルがプロンプトキャッシュ対応かどうかで分岐が必要**（Nova系・旧モデルは非対応の可能性があるため、失敗時はキャッシュなしで再試行するフォールバックを入れる）。

### 2-c. OpenAI: 対応不要（自動キャッシュ）

OpenAI はプロンプトキャッシュが自動適用のため実装変更なし。`usage` のキャッシュ関連フィールドのログ出力のみ追加。

### 2-d. spec.md へのキャッシュ仕様追記

対象: `versions/v0.8.3/spec.md`

レビュー実行APIの仕様にプロンプトキャッシュの動作（2回目実行時のコスト削減）を追記。

## Step 7: Structured Outputs によるフェーズ1（構造マッチング）堅牢化

対象: `backend/app/routers/review.py`（`/api/review/structure-matching`）、各プロバイダーサービス

- グループ定義（`groups[].doc_sections/code_symbols`）のJSONスキーマを定義
- プロバイダー別に構造化出力を実装:
  - **Anthropic**: `output_config.format`（json_schema）
  - **OpenAI**: `response_format`（json_schema, strict）
  - **Bedrock**: Converse API の `toolConfig`（tool use で代替）または対応モデルの構造化出力
- `_extract_json` の正規表現抽出はフォールバックとして残す（非対応モデル用）
- あわせてフロントの `getSimpleJudgment`（レポート本文の OK/NG キーワード数えによる判定）を、LLMに判定サマリJSONを出力させる方式に置き換える検討

## Step 8: ストリーミング対応

- バックエンド: 各プロバイダーにストリーミングメソッドを追加し、レビュー実行APIを SSE（`text/event-stream`）対応に
  - Anthropic: `messages.stream`
  - Bedrock: `converse_stream`
  - OpenAI: `stream=True`
- フロントエンド: `ExecutingScreen` / `SplitExecutingScreen` で逐次テキスト表示
- これにより「5分タイムアウト」問題を解消し、`maxTokens` の上限引き上げ（Claude系 64000 目安）が可能になる
- 既存の一括レスポンスAPIは後方互換のため残す

## Step 9: LLM呼び出しの非同期化・リトライ共通化

- 同期SDK呼び出しを `asyncio.to_thread` でラップ（organize と同方式に統一）、または各SDKの async クライアントに移行
- `LLMProvider` 基底クラスにリトライ（指数バックオフ、レート制限 429 / 5xx 対象）とタイムアウトを共通実装
- 3プロバイダーの重複コード（`execute_review` / `send_message` / `organize_markdown` / `test_connection`）を基底クラスにテンプレートメソッドとして集約し、各プロバイダーは「1回のAPI呼び出し」のみ実装する形に整理

## Step 10: トークン推定の一元化としきい値再調整

- バックエンドに `/api/estimate-tokens` を新設:
  - Anthropic系: `count_tokens` API で正確に計数
  - その他: 現行ヒューリスティック（日本語1.5/字）に統一
- `review.py` / `split.py` / `markdown_organizer.py` / フロント `useTokenEstimation.ts` の推定ロジックをこのAPIに集約
- フロントの `WARNING_THRESHOLD = 100000` を撤廃し、選択中モデルのコンテキスト長に基づく動的しきい値に変更（現行 Claude 系は1Mトークン）
- 分割レビューの推奨判定（「このサイズなら一括でいける」ガイダンス表示）を追加

## Step 11: テスト追加（v0.9.0 分）

- 構造化出力のスキーマ検証テスト
- ストリーミングのSSEイベント形式テスト

- `/api/estimate-tokens` のテスト
- ルーターのHTTPレベル統合テスト（TestClient経由）を新設 — 現状の穴を埋める

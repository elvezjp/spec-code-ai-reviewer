# v0.9.0 マッピングモード実装計画書

**作成日**: 2026-02-10
**対象バージョン**: v0.9.0
**ベースバージョン**: v0.8.0
**関連PR**: [#34](https://github.com/elvezjp/spec-code-ai-reviewer/pull/34)

## 1. 概要

### 1.1 背景

既存の「突合モード」は設計書とコードの **整合性検証**（差異・問題点の発見）に焦点を当てている。一方、「設計書のどの項目が、ソースコードのどこで実装されているか」を **トレーサビリティ** として可視化したいニーズがある。

v0.8.0 で導入されたセマンティック分割レビュー機能（md2map / code2map）により、設計書とコードの構造解析基盤が整った。この基盤を活用し、設計書項目とコード実装箇所の対応付けを行う「マッピングモード」を追加する。

### 1.2 目的

設計書の各項目（見出し、要件、機能など）がソースコードのどこで実装されているかを特定し、マッピング表として可視化する。

### 1.3 v0.8.0 からの差分

| 観点 | v0.8.0（突合モード） | v0.9.0（マッピングモード追加） |
|------|---------------------|-------------------------------|
| モード | 突合モードのみ | 突合モード + マッピングモード |
| 目的 | 整合性検証（差異・問題点の発見） | 設計項目と実装箇所の対応付け |
| プリセット | 突合用 8種 | 突合用 8種 + マッピング用 3種 |
| システムプロンプト | 突合用 | モード別に自動切り替え |
| 構造マップ | 分割時のみ生成 | **常に生成し、AIに構造情報として提供** |
| 分割レビュー | 構造マッチング → グループレビュー → 統合 | 同一フロー（プロンプトのみ変更） |
| 簡易判定 | 不整合キーワード検索 | カバレッジ率による判定 |
| 出力 | レビューレポート | マッピング表 + カバレッジレポート |

### 1.4 md2map / code2map の活用

v0.8.0 では分割レビュー時のみ md2map / code2map を使用していたが、v0.9.0 では **`useStructureMap=true` の場合、レビュー実行開始時に構造マップ（MAP.json）を生成** し、AIへの入力として提供する。

#### 構造マップ生成のタイミング

v0.8.0 の分割設定セクションのプレビューでは、「分割」を選択した側のみ MAP.json が生成される（一括側は生成されない）。そのため、`useStructureMap=true` の場合は **レビュー実行開始時に構造マップ生成ステップを実行** する。

- **判定条件**: `useStructureMap` フラグで制御（モードではなくフラグで判定）
- **スキップロジック**: 分割プレビューで既に MAP.json が生成済みの側はスキップし、未生成の側のみ新たに生成する
- **対象**: 設計書 MAP.json（md2map）+ 各コードファイル MAP.json（code2map）
- **タイミング**: レビュー実行ボタン押下後、AI呼び出し前（前処理として実行）

#### 構造マップの効果

MAP.json には設計書・コードの構造メタデータが含まれる：

- **設計書 MAP.json**（md2map）: セクションID（MD1, MD2...）、見出し名、階層パス、行範囲
- **コード MAP.json**（code2map）: シンボルID（CD1, CD2...）、クラス/メソッド名、型、行範囲

これをAIに渡すことで、マッピング精度が向上する（設計書のどの見出しがコードのどのクラス/メソッドに対応するかを、構造情報を根拠に判定できる）。

#### 利用場面

| API | 渡す構造マップ | 用途 |
|-----|--------------|------|
| `/api/review`（一括） | 設計書MAP.json + コードMAP.json | AIが構造を把握した上でレビュー/マッピング |
| `/api/review/group`（分割グループ） | 該当グループのMAP.json | グループ内の構造を把握した上でレビュー/マッピング |
| `/api/review/integrate`（分割統合） | 全体のMAP.json | 統合時に全体構造を参照 |

#### useStructureMap オプション

構造マップの利用はオプションとし、`useStructureMap` フラグで制御する。

| モード | useStructureMap デフォルト | 理由 |
|--------|--------------------------|------|
| マッピングモード | `true` | 構造情報がマッピング精度に直結 |
| 突合モード | `false` | 既存動作を維持（将来的に有効化可能） |

> **将来拡張**: 突合モードでも `useStructureMap=true` にすることで、構造を考慮したレビューが可能。v0.9.0 ではマッピングモードのみデフォルト有効とする。

## 2. 要件

### 2.1 機能要件

1. **モード切り替え**
   - 画面上部でタブによる切り替え（突合モード / マッピングモード）
   - 選択中のモードは localStorage に保存（既存の LLM モデル・プリセット選択と同様）
   - 初期表示は localStorage から復元、未設定時は突合モード

2. **入力**
   - 入力ファイルは既存と同一（設計書 Excel、ソースコード）
   - 前処理も同一（Markdown 変換、行番号付与）

3. **構造マップ生成**（`useStructureMap=true` 時）
   - レビュー実行開始時に、md2map / code2map で MAP.json を生成する（AI呼び出し前の前処理）
   - `useStructureMap` フラグで生成の要否を判定（モードではなくフラグで判定）
   - 分割プレビューで既に生成済みの MAP.json がある場合はスキップ（未生成の側のみ新たに生成）
   - 既存の `/api/split/markdown`、`/api/split/code` を利用（MAP.json 部分のみ使用）
   - 生成した MAP.json はフロントエンドで保持し、レビューAPIへ渡す

4. **処理**
   - 一括レビュー: 既存の `/api/review` を使用（モードパラメータ + 構造マップ追加）
   - 分割レビュー: 既存の分割レビューフロー（構造マッチング → グループレビュー → 統合）を使用（プロンプトのみモード別に変更、各APIに構造マップを渡す）
   - システムプロンプトはマッピング専用のものを使用
   - `useStructureMap` オプションで構造マップの利用を制御（マッピングモード: デフォルト `true`、突合モード: デフォルト `false`）
   - 2回実行のロジックも同一

5. **出力**
   - マッピング結果の専用表示画面（簡易判定のみモード別、他は共通）
   - 一式ダウンロード機能は同一

### 2.2 非機能要件

- v0.8.0 をコピーして v0.9.0 として実装
- 既存の突合モードは変更なし（後方互換維持）
- 分割レビューフローのコードは共通化（プロンプト差し替えのみ）

#### 2.4 結果表示コンポーネントの共通化

既存の `ReviewResult.tsx` をベースに、突合モード・マッピングモード両対応に拡張する。

**共通化方針**:

- **見出しの共通化**: モードによらず同じ見出しを使用
  - 「レビュー情報」→「実行情報」
  - 「レビュー実行データ一式ダウンロード」→「実行データ一式ダウンロード」

- **各セクションの共通化方針**:
  | セクション | 共通化 | カスタマイズ内容 |
  |-----------|-------|----------------|
  | ヘッダー + タブ切り替え | 完全共通 | なし |
  | 簡易判定 | 構造共通 | 判定ロジックとステータス表示内容のみモード別 |
  | 実行情報 | 完全共通 | なし（見出しを共通化） |
  | 詳細レポート | 完全共通 | なし |
  | 実行データ一式ダウンロード | ほぼ共通 | ZIPファイル名のみモード別（`review-result.md` / `mapping-result.md`） |

#### 2.5 構造マップの生成（レビュー実行時）

**ファイル**: `versions/v0.9.0/frontend/src/features/reviewer/hooks/useStructureMap.ts`（新規）

`useStructureMap=true` の場合、レビュー実行開始時に構造マップ（MAP.json）を生成するフック。
分割プレビューで既に生成済みのものはスキップする。

```typescript
import type { StructureMapInfo, DocumentMapEntry, CodeMapEntry } from '../types'

export function useStructureMap() {
  const [structureMap, setStructureMap] = useState<StructureMapInfo | null>(null)
  const [isGenerating, setIsGenerating] = useState(false)

  /**
   * 構造マップを生成（レビュー実行開始時に呼び出す）
   * 分割プレビューで既に生成済みのものはスキップする
   *
   * @param existingDocumentMap - 分割プレビューで生成済みの設計書MAP.json（未生成の場合 null）
   * @param existingCodeMaps - 分割プレビューで生成済みのコードMAP.json（未生成の場合 空配列）
   */
  const generateStructureMap = useCallback(async (
    specMarkdown: string,
    specFilename: string,
    codeFiles: { filename: string; content: string }[],
    existingDocumentMap: DocumentMapEntry[] | null,
    existingCodeMaps: { filename: string; entries: CodeMapEntry[] }[],
  ) => {
    setIsGenerating(true)

    // 1. 設計書の MAP.json（未生成の場合のみ生成）
    let documentMap: DocumentMapEntry[]
    if (existingDocumentMap) {
      documentMap = existingDocumentMap  // 分割プレビューで生成済み → スキップ
    } else {
      const docResult = await api.splitMarkdown({
        content: specMarkdown,
        filename: specFilename,
        maxDepth: 2,
      })
      documentMap = docResult.parts  // MAP.json 相当
    }

    // 2. 各コードファイルの MAP.json（未生成のファイルのみ生成）
    const existingCodeMapFiles = new Set(existingCodeMaps.map(m => m.filename))
    const codeMaps = await Promise.all(
      codeFiles.map(async (file) => {
        // 既に生成済みのファイルはスキップ
        const existing = existingCodeMaps.find(m => m.filename === file.filename)
        if (existing) {
          return existing
        }
        // 未生成のファイルは新たに生成
        const codeResult = await api.splitCode({
          content: file.content,
          filename: file.filename,
        })
        return {
          filename: file.filename,
          entries: codeResult.parts,  // MAP.json 相当
        }
      })
    )

    setStructureMap({ documentMap, codeMaps })
    setIsGenerating(false)
  }, [])

  return { structureMap, isGenerating, generateStructureMap }
}
```

## 7. 設計上の要点

### 7.1 既存コードとの共通化

マッピングモードは突合モードと **UIフロー・コンポーネント構造を完全に共通化** し、以下のみモード別に差し替える:

1. **プリセットカタログ**: モードに応じたプリセット一覧
2. **システムプロンプト**: モードに応じたデフォルトプリセット
3. **プロンプトビルダー**: API呼び出し時のユーザーメッセージ/プロンプト
4. **構造マップ利用**: マッピングモードでは `useStructureMap=true`（突合モードでは `false`）
5. **簡易判定ロジック**: 突合=キーワード検索、マッピング=カバレッジ率
6. **ZIPファイル名**: `review-result.md` / `mapping-result.md`

これにより:
- 新規ファイルは `ModeSelector.tsx` と `useStructureMap.ts` の2ファイルのみ
- 分割レビュー（SplitExecutingScreen, SplitSettingsSection）はそのまま両モードで利用
- 保守コスト最小化

### 7.4 構造マップの生成と利用フロー

```
【分割設定セクション（プレビュー時 - ユーザー操作）】

  ※ v0.8.0 の既存動作:「分割」を選択した側のみ MAP.json が生成される

  設計書を「分割」に設定 → /api/split/markdown (md2map) → 設計書 MAP.json ✓
  設計書を「一括」に設定 → 生成されない                  → 設計書 MAP.json ✗

  コードを「分割」に設定 → /api/split/code (code2map)   → コード MAP.json ✓
  コードを「一括」に設定 → 生成されない                  → コード MAP.json ✗


【レビュー実行開始時（useStructureMap=true の場合 - 自動実行）】

  ┌─────────────────────────────────────────────────────────────┐
  │  構造マップ生成ステップ（AI呼び出し前の前処理）              │
  │  ※ useStructureMap フラグで実行の要否を判定                 │
  │                                                             │
  │  1. 設計書 MAP.json の確認                                  │
  │     ├─ 分割プレビューで生成済み → スキップ                  │
  │     └─ 未生成 → /api/split/markdown (md2map) で生成         │
  │                                                             │
  │  2. 各コードファイル MAP.json の確認                         │
  │     ├─ 分割プレビューで生成済み → スキップ                  │
  │     └─ 未生成 → /api/split/code (code2map) で生成           │
  │                                                             │
  │  → StructureMapInfo として保持                               │
  │     {                                                       │
  │       documentMap: [MD1, MD2, ...],                         │
  │       codeMaps: [{ filename, entries: [CD1, CD2, ...] }]    │
  │     }                                                       │
  └─────────────────────────────────────────────────────────────┘

  ※ useStructureMap=false（突合モードのデフォルト）の場合はスキップ


【レビュー実行時のAPIリクエスト】

  一括レビュー:
    /api/review
      mode = "mapping"
      useStructureMap = true     ← マッピングモード時デフォルト
      structureMap = {           ← 上記ステップで取得した MAP.json
        documentMap: [MD1, MD2, ...],
        codeMaps: [{ filename, entries: [CD1, CD2, ...] }, ...]
      }

  分割レビュー:
    /api/group-review
      mode = "mapping"
      useStructureMap = true
      structureMap = { ... }     ← 該当グループの MAP エントリのみ

    /api/integrate
      mode = "mapping"
      useStructureMap = true
      structureMap = { ... }     ← 全体の MAP.json


【生成パターン例】

  ケース1: 両方「一括」（MAP.json 未生成）
    → レビュー実行時に設計書・コード両方の MAP.json を新規生成

  ケース2: 設計書「分割」＋コード「一括」
    → 設計書 MAP.json はスキップ、コード MAP.json のみ新規生成

  ケース3: 両方「分割」（MAP.json 生成済み）
    → 両方スキップ（追加のAPI呼び出しなし）
```

### 7.5 分割レビューとマッピングモードの連携

v0.8.0 の分割レビューフローをマッピングモードで活用する際の対応:

```
一括レビュー:
  突合モード:
    /api/review (mode=review, useStructureMap=false)  → 突合レポート
  マッピングモード:
    /api/review (mode=mapping, useStructureMap=true, structureMap=...)  → マッピングレポート

分割レビュー:
  突合モード:
    /api/structure-matching (mode=review)                          → 関連グループ特定
    /api/group-review (mode=review, useStructureMap=false) × N     → 各グループ突合結果
    /api/integrate (mode=review, useStructureMap=false)             → 統合突合レポート

  マッピングモード:
    /api/structure-matching (mode=mapping)                          → 設計項目↔コード要素の対応推定
    /api/group-review (mode=mapping, useStructureMap=true) × N     → 各グループマッピング結果
    /api/integrate (mode=mapping, useStructureMap=true)             → 統合マッピングレポート
```

分割レビューのコード（フロントエンド・バックエンド）は完全に共通。プロンプトビルダーのみがモード・構造マップに応じて異なるプロンプトを生成する。

### 7.6 useStructureMap オプションの設計

`useStructureMap` は構造マップに関する **すべての動作を制御する単一のフラグ** である。モード（突合/マッピング）はこのフラグのデフォルト値を決定するだけで、実際の動作はすべて `useStructureMap` で判定する。

#### フラグの制御範囲

| 制御対象 | useStructureMap=true | useStructureMap=false |
|----------|---------------------|----------------------|
| 構造マップ生成（レビュー実行時） | 生成する（既存分はスキップ） | 生成しない |
| プロンプトへの構造マップ組み込み | 組み込む | 組み込まない |
| APIリクエストの structureMap フィールド | MAP.json を送信 | 送信しない |

#### デフォルト値の導出

| 項目 | 内容 |
|------|------|
| 型 | `boolean` |
| デフォルト値 | `false` |
| マッピングモード時 | フロントエンドが `true` を設定 |
| 突合モード時 | フロントエンドが `false` を設定（将来的に切り替え可能） |

```typescript
// フロントエンドでのデフォルト値導出（唯一の箇所）
const useStructureMap = reviewMode === 'mapping'
```

#### バックエンドの責務

- `useStructureMap=true` かつ `structureMap` が存在する場合のみプロンプトに構造マップを含める
- `structureMap` が `null` の場合は `useStructureMap=true` でも構造マップセクションは出力しない
- バックエンドはモード（review/mapping）を意識せず、`useStructureMap` フラグのみで判定する

> **将来拡張**: 突合モードでも `useStructureMap` をUIからトグルできるようにすることで、構造を考慮したレビューが可能になる。フラグベースの設計により、モードとは独立して制御できる。

# v0.9.0 マッピングモード実装計画書

**作成日**: 2026-02-10
**対象バージョン**: v0.9.0
**ベースバージョン**: v0.8.0
**関連PR**: [#34](https://github.com/elvezjp/spec-code-ai-reviewer/pull/34)

## 1. 概要

### 1.1 背景

既存の「突合モード」は設計書とコードの **整合性検証**（差異・問題点の発見）に焦点を当てている。一方、「設計書のどの項目が、ソースコードのどこで実装されているか」を **トレーサビリティ** として可視化したいニーズがある。

v0.8.0 で導入されたセマンティック分割レビュー機能（md2map / code2map）により、設計書とコードの構造解析基盤が整った。この基盤を活用し、設計書項目とコード実装箇所の対応付けを行う「マッピングモード」を追加する。

### 1.2 目的

設計書の各項目（見出し、要件、機能など）がソースコードのどこで実装されているかを特定し、マッピング表として可視化する。

### 1.3 v0.8.0 からの差分

| 観点 | v0.8.0（突合モード） | v0.9.0（マッピングモード追加） |
|------|---------------------|-------------------------------|
| モード | 突合モードのみ | 突合モード + マッピングモード |
| 目的 | 整合性検証（差異・問題点の発見） | 設計項目と実装箇所の対応付け |
| プリセット | 突合用 8種 | 突合用 8種 + マッピング用 3種 |
| システムプロンプト | 突合用 | モード別に自動切り替え |
| 分割レビュー | 構造マッチング → グループレビュー → 統合 | 同一フロー（プロンプトのみ変更） |
| 簡易判定 | 不整合キーワード検索 | カバレッジ率による判定 |
| 出力 | レビューレポート | マッピング表 + カバレッジレポート |

### 1.4 md2map / code2map の活用

v0.8.0 で導入された分割機能をマッピングモードでも活用する。

| ツール | 突合モードでの用途 | マッピングモードでの用途 |
|--------|-------------------|------------------------|
| md2map | 設計書の意味単位分割 | 設計書項目の構造抽出（マッピング元） |
| code2map | コードのクラス/関数分割 | 実装箇所の構造抽出（マッピング先） |
| 構造マッチング API | 関連グループの特定 | 設計項目→コード箇所の対応付け |

マッピングモードでは、分割レビューの構造マッチング結果を「マッピングの初期推定」として利用し、AIによる詳細マッピングの精度を向上させる。

## 2. 要件

### 2.1 機能要件

1. **モード切り替え**
   - 画面上部でタブによる切り替え（突合モード / マッピングモード）
   - 選択中のモードは localStorage に保存（既存の LLM モデル・プリセット選択と同様）
   - 初期表示は localStorage から復元、未設定時は突合モード

2. **入力**
   - 入力ファイルは既存と同一（設計書 Excel、ソースコード）
   - 前処理も同一（Markdown 変換、行番号付与）

3. **処理**
   - 一括レビュー: 既存の `/api/review` を使用（モードパラメータ追加）
   - 分割レビュー: 既存の分割レビューフロー（構造マッチング → グループレビュー → 統合）を使用（プロンプトのみモード別に変更）
   - システムプロンプトはマッピング専用のものを使用
   - 2回実行のロジックも同一

4. **出力**
   - マッピング結果の専用表示画面（簡易判定のみモード別、他は共通）
   - 一式ダウンロード機能は同一

### 2.2 非機能要件

- v0.8.0 をコピーして v0.9.0 として実装
- 既存の突合モードは変更なし（後方互換維持）
- 分割レビューフローのコードは共通化（プロンプト差し替えのみ）

#### 2.4 結果表示コンポーネントの共通化

既存の `ReviewResult.tsx` をベースに、突合モード・マッピングモード両対応に拡張する。

**共通化方針**:

- **見出しの共通化**: モードによらず同じ見出しを使用
  - 「レビュー情報」→「実行情報」
  - 「レビュー実行データ一式ダウンロード」→「実行データ一式ダウンロード」

- **各セクションの共通化方針**:
  | セクション | 共通化 | カスタマイズ内容 |
  |-----------|-------|----------------|
  | ヘッダー + タブ切り替え | 完全共通 | なし |
  | 簡易判定 | 構造共通 | 判定ロジックとステータス表示内容のみモード別 |
  | 実行情報 | 完全共通 | なし（見出しを共通化） |
  | 詳細レポート | 完全共通 | なし |
  | 実行データ一式ダウンロード | ほぼ共通 | ZIPファイル名のみモード別（`review-result.md` / `mapping-result.md`） |

- **簡易判定のモード別表示**:
  - 突合モード: 既存の `ng`/`warning`/`ok` 判定（不整合キーワード検索）
  - マッピングモード: カバレッジ率による `ng`/`warning`/`ok` 判定

```typescript
// マッピング用簡易判定ロジック
function getSimpleMappingJudgment(reportText: string): SimpleMappingJudgment {
  // レポート内のキーワードからカウントを抽出
  // 1. 設計書項目件数: マッピング一覧テーブルの行数 + 未マッピング項目リストの件数
  // 2. マッピング件数: マッピング一覧テーブルの行数
  // 3. 未マッピング件数: 「未マッピング」セクションの項目数
  // 4. カバレッジ率: マッピング件数 / 設計書項目件数 * 100

  // ステータス判定:
  // - 判定不能（パース失敗等） → 'ng'
  // - 設計書項目件数が0 → 'ng'
  // - カバレッジ0% → 'ng'
  // - カバレッジ100% → 'ok'
  // - カバレッジ1-99% → 'warning'
}
```

## 7. 設計上の要点

### 7.1 既存コードとの共通化

マッピングモードは突合モードと **UIフロー・コンポーネント構造を完全に共通化** し、以下のみモード別に差し替える:

1. **プリセットカタログ**: モードに応じたプリセット一覧
2. **システムプロンプト**: モードに応じたデフォルトプリセット
3. **プロンプトビルダー**: API呼び出し時のユーザーメッセージ/プロンプト
4. **簡易判定ロジック**: 突合=キーワード検索、マッピング=カバレッジ率
5. **ZIPファイル名**: `review-result.md` / `mapping-result.md`

これにより:
- 新規コンポーネントは `ModeSelector.tsx` の1ファイルのみ
- 分割レビュー（SplitExecutingScreen, SplitSettingsSection）はそのまま両モードで利用
- 保守コスト最小化

### 7.4 分割レビューとマッピングモードの連携

v0.8.0 の分割レビューフローをマッピングモードで活用する際の対応:

```

  突合モード:     /api/review (mode=review)  → 突合レポート
  マッピングモード: /api/review (mode=mapping) → マッピングレポート

分割レビュー:
  突合モード:
    /api/structure-matching (mode=review)  → 関連グループ特定
    /api/group-review (mode=review) × N    → 各グループ突合結果
    /api/integrate (mode=review)           → 統合突合レポート

  マッピングモード:
    /api/structure-matching (mode=mapping) → 設計項目↔コード要素の対応推定
    /api/group-review (mode=mapping) × N   → 各グループマッピング結果
    /api/integrate (mode=mapping)          → 統合マッピングレポート
```

分割レビューのコード（フロントエンド・バックエンド）は完全に共通。プロンプトビルダーのみがモードに応じて異なるプロンプトを生成する。
